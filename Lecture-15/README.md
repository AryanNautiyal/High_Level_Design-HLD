# Data Pages

    -- So in data pages we store headers, data records and offset 

    -- So our actual records or tables are stored in data pages format

    -- So our whole table which is a logical representation when we talk about actually representing it in memory our DBMS divides 
        it into data pages 

    -- So data pages consists of 3 parts :
                
                (1) Data Records 

                    -- So suppose we have 1 Million records in our table so our DBMS will divide this 1 Million records into 
                        multiple data pages

                    -- Like we can say that our data page 1 holds 40 records then data page 2 holds next 40 records

                    -- So generally the size of data page that a DBMS has is 8 KB (can be 16 KB also) so as we know 8 KB = 8192
                        bytes 

                    -- So this is the breakdown of the size each component of data page takes

                            Headers : 96 Bytes

                            Data Records : 8060 Bytes

                            Offset : 36 Bytes


                    -- So if we assume that in our table each row takes 32 bytes so we can say that to store each user's data we 
                        need 32 bytes

                    -- So each row takes 32 bytes and data records can hold 8060 bytes of data

                            So number of records we can store in our data records in 1 data page = 8060 / 32 = ~ 251 rows 

                    -- So if we divide our table which consists of 1 Million entries into data pages then 

                            Number of data pages required to store all the entries = 1 Million / 251 = ~ 3984 data pages 

                    -- So in conclusion we need 3984 data pages just to represent our data table consisting of 1 Million records


                (2) Headers 

                    -- Headers store information about the page number and checksum 

                    -- As in above example we saw that 3984 data pages will be required to store 1 Million records so we will give
                        each data page a number so as to determine which data is stored in which data page 

                    -- Another thing is checksum so checksum is a unique code generated by combining all the data stored in the 
                        data records so we can either hash the whole data or can perform other operations to obtain a checksum value

                    -- So if the checksum value when it is again found by performing same operations again on the data in the data 
                        records and it doesn't match with the previous one then it can be easily determined that the data has been 
                        changed inside that data page 

                    -- So using checksum it can be determined whether the data in the data records of that data page is corrupted 
                        or not

                    -- So if write operation is done on data then DBMS will also calculate and update the new checksum value in the 
                        headers of the data page

                    -- So each page will have it's own checksum and it's own page number (1 checksum for entire page)

                
                (3) Offset

                    -- Offset is an array of indexed rows 

                    -- Inside data records the data can be unsorted like userID = 25 comes before userID = 9 so there's no point of
                        B+ Tree use if we are ultimately going to search the record linearly in O(N) time

                    -- So offset helps by keeping an indexed array in which the data records in that data pages are kept in sorted 
                        order (PK is sorted) so by looking at offset it will point to exact location of data in that data page hence
                        we will find data in less time

                    -- So if client request to see data of UserID = 25 then using B+ tree it will locate the data page and using 
                        the offset will locate the data inside that data page


    -- Data pages are managed by the DBMS 

    -- All the data pages are ultimately stored in the memory 

                    

# Data Blocks 

    -- Sector is the smallest unit in the hard disk 

    -- Combining one or more sector forms a data block 

    -- So data block can be of range 8 KB - 64 KB (sector is 4 KB only)

    -- So our data pages can be stored anywhere on the disk 

    -- So our data blocks stores the data pages and these data pages stores the data records 

    -- Data block is the smallest possible value we can expect from an IO operation

    -- So when we do any read or write operation our DB will atleast bring one data block or will store one data block

        {
            As we know the hardware can send only a sector so if we want a data block what OS does is that it sends read command to read 8 sectors so hardware sends data of 8 sectors one by one and then disk controller glues these 8 sectors together 
            forming a data block and then it is put in RAM 

            As OS feels sectors are too small so they deal with data block

            If the OS had to manage every 512-byte sector, the Metadata (the map of where everything is) would be so large it would 
            stay in RAM

            By dealing in Blocks, the OS reduces the "bookkeeping" and makes I/O much more efficient.

            In short if the OS tried to manage every individual physical sector, your computer would crawl to a halt just trying to 
            keep track of where everything is.

            Summary of the Flow

                    (1) Request: OS asks for 1 Block (e.g., 4 KB).

                    (2) Command: Disk Controller translates this to 8 Sectors (e.g., 512B each).

                    (3) Action: The hardware reads the 8 sectors from the physical platter/flash.

                    (4) Assembly: The Controller "glues" them in its buffer.

                    Result: The OS receives a single, complete Data Block in RAM.
        }


# Indexing in DB


    -- So let's assume we don't have any indexing or primary key so if we run this query 

                SELECT * FROM Users WHERE UserID = 101;

    -- So what will happen is that our server will query the SQL DB and our SQL DB will have a hard disk 

    -- So the user table will be kept in different data blocks and we don't have any indexing or anything with which we can find the
        data block having UserID = 101 data 

    -- So SQL DB will just one by one pick up data block and will search for the data in the data block

    -- So if we assume each data block consist of 2 data pages (data block size = 16 KB) so we will fetch one data block and will 
        search for UserID = 101 in both the pages one by one 

    -- So if in data page 1 the data is not found then it will search in data page 2 and if not present in both then will tell hard 
        disk to bring data block 2 and so on

        {
            Hard disk drive bring back the bits or data from hard disk 
            
            The Hard Disk Drive is responsible for the physical movement. It moves the mechanical arm (actuator) to the right track 
            and waits for the spinning Hard Disk platter to bring the specific sectors under the read head. The head then picks up 
            the raw electrical/magnetic pulses—the bits.

            And disk controller makes data block from it

            As those raw bits come off the platter, the Disk Controller (the chip) catches them. It performs three vital tasks:

                -- Error Correction: It uses the Checksum/ECC we discussed earlier to make sure no bits were flipped during the 
                                    physical read.

                -- Buffering: It holds the sectors in its own small cache.

                -- The "Glue": It assembles those 8 or 16 sectors into the 16 KB Data Block that the OS is waiting for.
        }

    -- So from hard disk the data is brought into the RAM and then in RAM the SQL DB will check for the data

    -- So in this it will take O(N) time complexity as we need to fetch the whole table and search for the data we want

    -- So if we consider above example then we have like 3984 data pages and each data page consists of 251 rows of data 

    -- So dependency on hard disk is more in this case as we are fetching each data block and comparing data and as we know that 
        hard disk is slow so it's time complexity can go higher than O(N) also in case of 1 Million or high number of data 

    -- So without indexing it is a very time taking process

    -- So indexing is used to increase the performance of our DB queries (making queries run faster)

    -- So we want to reduce the time taken to search a particular data 

    -- So if we use BST then our search time can be halved as we can go to left or right child and if we go to any one of them 
        in the next level the tree is halved meaning we don't need to search all the data in the other side 

    -- So we use B+ Trees for indexing (as BST can be skewed which might make again O(N) search time and then we moved to AVL tree 
        but our disk gives each sector so if only last 10 bytes is the data that we were searching for then we will have to read 
        whole 4 KB block to get 10 bytes data so we use B+ Tree so in this in each sector whole 4 KB data will be of data only as 
        many keys are stored at a particular level and in it's left and right child also so size of all those data combined will be 
        4 KB so no operation is wasted)

    -- So we reduced our searching time from O(N) --> O(log N) [In log N there is a base " f " which is the fan-out (how many 
        children each node has)]


        [B-Trees & B+ Trees explained refer to PDF]

    -- In B+ Trees leaf nodes are connected and intermediate nodes also store left parent value 

    -- In B+ Tree

            (.) Left Node < Current Value

            (.) Right Node >= Current Value 

    -- In leaf node in the left of value address is there of the data stored in DB and at the far right in a leaf node address will
        be stored to the next leaf node in B+ Tree

    -- So in SQL DB B+ Tree is used 

    -- So our DBMS will make a B+ Tree with the help of primary key in DB (will use Primary Key as index) so due to this index will
        be created (DBMS itself decides order of B+ Tree)

    -- So if client runs query to fetch all details of user whose userID = 19 (SELECT * FROM Users WHERE UserID = 19) so DBMS will 
        look in B+ Tree for UserID = 19 then after finding it there will be the information of the data page number in which it will
        be found and then DBMS will map this data page number to data block and will fetch the data

    -- So in B+ Trees the leaf node has all the possible values there can be in a column using which index was created and we can do
        range queries also as all leaf nodes are joined and in leaf node can implement binary search also to find data in O(log N) 
        time (hence B+ Tree is preferred over B Tree)

    -- So as soon as we create a primary key DBMS will internally create indexing using the PK



    
    # Types of Indexing 

        (1) Clustered Indexing 

            -- So in clustered indexing the leaf nodes also contain the information that offset has 

            -- So in leaf node it will contain page number of data page and also where the data is stored in that data page also

            -- So we won't be needed to look in offset and search for data location in that data page instead we go directly to that
                location

            -- There can only be one cluster index per table, the DBMS automatically makes the cluster index using PK or if PK is 
                not there then using unique key

            -- In clustered indexing we can only create one as in this the indexing is done based on physical arrangement of data in
                memory so we can arrange data in memory in one way only so hence only one can be created


        (2) Non-Clustered Indexing 

            -- In this the leaf node contains the page number in which the data is stored 

            -- Then after we find that data page we do searching in offset to find the precise location of the data in the data page

            -- There can be multiple non-clustered index per table 

            -- It can be multiple as it is kind of like a map of where the data is, the physical arrangement of data is same but 
                different maps are created to reach this data

    
    -- We cannot index each column in the table as the index also occupies space in DB (almost 20% of the data stored in DB) so we
        need to carefully think whether to index a column or not
